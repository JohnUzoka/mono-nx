# Porting mono to the switch homebrew toolchain - Part 2

Last year I worked on porting Mono to the Switch and wrote a lengthy blog post about many of the issues I ran into. While the port did technically work, it still bugged me that it was not running any "real" program. If you haven't read Part 1 of this write-up, you can find it [here](https://github.com/exelix11/mono-nx/blob/master/notes/writeup.md).

After some thought and consultation with friends, I decided to try to port a real game using mono-nx to prove that it is actually usable. The whole process surfaced several issues that I had not encountered in the demo programs included with the project and greatly helped improve the maturity of the port, this is what I will be writing about in this second part of the write-up.

While the previous write-up was a sequential narrative of the porting process, this one is more of a collection of notes I took during the work. While I will try to keep it chronological, in practice most of these issues were discovered in parallel while working on other issues, so the order of the sections is not necessarily the order in which they were discovered.

## Picking the target

I wanted to port something reasonably complex rather than just another demo. The game also had to be written entirely in C# and use rendering libraries supported by the Switch portlibs. C# is best known for being used in Unity, but that was not a realistic target since the unity runtime itself is not open source and, even if it were, porting it would have been another huge project on its own.

I used the SteamDB [engine search](https://steamdb.info/tech/) to find games that use either Godot (which already has a Switch port without C# support) or XNA/MonoGame. MonoGame in particular looked promising since it only depends on native libraries like OpenGL and SDL2, which are already supported on the Switch. However, I quickly realized that most games on Steam are commercial and closed source. Even if I avoided DRM by choosing a free game, I would still have had to deal with porting a potentially obfuscated binary rather than working from clean source code. This is something I want to try in the future, but I excluded it early on for this project.

In the end, after discussing it with some online friends, I picked osu!stream. While the desktop version of osu! is well known, [osu!stream](https://github.com/ppy/osu-stream) is a lesser-known, separate mobile version of the game that was open-sourced quite some time ago. Since it is written as a very self-contained game using only raw OpenTK for rendering, it was a perfect candidate. It did take some effort, mostly in terms of debugging and fixing runtime bugs, but here is a video of the game running on Switch:

(forgive the choppiness, it was recorded with [SysDVR](https://github.com/exelix11/sysdvr), the game runs at stable 60fps on console)

Given the unofficial nature of this port and the fact that osu itself is trademarked, this port is called Nx!stream. The source code is [available on GitHub](https://github.com/exelix11/nx-stream) under the original MIT license.

## Porting C# games

This section goes over what I had to do to get the game running on the Switch. I will not go into much detail about the port itself, since i want to focus on Mono rather than a specific game. However, the information may still be useful, especially regarding how I handled third-party dependencies.

First, I had to port OpenTK to the Switch, as it is the main dependency of the project. OpenTK is a C# wrapper around OpenGL, and most of its logic just works since it ends up invoking the native OpenGL functions. I only had to create Switch-specific implementations for the window and [context creation parts](https://github.com/exelix11/osu-stream-nx/blob/master/OpenTK/OpenTK/Platform/Egl/EglLibnxPlatformFactory.cs) of the code. The biggest challenge was getting OpenTK to work with Mono AOT, since it uses reflection and dynamic delegates, both of which are not supported by the AOT compiler. I ended up writing a [small tool](https://github.com/exelix11/osu-stream-nx/blob/master/OpenTK/ReflectionGenerator/Program.cs) that generates the glue code needed to avoid reflection and determine the delegate types at build time. The tool's output is deterministic, so I committed it to the repository. While this is a rather outdated version of OpenTK, it may be useful for porting other games; you can find the source code in the osu-stream-nx repository.

Additionally, I had to enable the [compatibility mode for legacy OpenGL](https://github.com/exelix11/osu-stream-nx/blob/master/OpenTK/OpenTK/Platform/Egl/EglLibnxPlatformFactory.cs#L154) and make sure the entrypoints are loaded in the [EGL context](https://github.com/exelix11/osu-stream-nx/blob/master/OpenTK/OpenTK/Platform/Libnx/LibnxGraphicsContext.cs#L21). This is because osu!stream is an older game that uses the fixed-function pipeline. Actually, this tiny detail almost caused me to give up on the port since no switch OpenGL example I could find supported the fixed-function pipeline. At some point a friend mentioned that mesa actually supports `EGL_CONTEXT_OPENGL_COMPATIBILITY_PROFILE_BIT_KHR` and that got me back on track.

After confirming that OpenTK could initialize a window and render to it using a sample program, I started working on the game itself. The game runs on desktop, android and ios, as such it is very portable with most platform-specific code being abstracted through interfaces, I only had to implement the Switch-specific ones. Initially, I created stubs for all of them and created a new `.csproj` from scratch for the Switch platform. I added the individual source files to the project one by one until I was able to build the game. Then I gradually removed the stubs and implemented the platform-specific code via libnx P/Invoke.

The biggest efforts were the background audio engine and text rendering. For audio, I had to remove the closed-source BASS library and replace it with OpenAL, which is conveniently also part of OpenTK and available on the Switch. To make this work, I also had to introduce some new third-party native libraries for MP3 and AAC audio decoding. I tried some fully managed decoders, but they were too slow and caused long loading times.

Text rendering was very annoying to figure out because the game does not have a text rendering engine and instead uses platform-specific APIs to rasterize text to OpenGL textures. Initially, I tried a [managed implementation of System.Drawing](https://docs.wisej.com/system.drawing.managed/concepts/), but it was too slow, destroying the frame rate every time a text object had to be updated. I ended up using fontstash, its OpenGL backend, and a bunch of hacks to get it somewhat working. I am not happy with this solution, but I did not want to get trapped in the intricacies of text rendering while I had more pressing Mono runtime work to do.

I am glossing over some additional work, such as docked/handheld detection, but those details are best explained by reading the code.

## pthread APIs that never fail (until they do)

While I was working on this, the switch firmware 21.0 dropped. It broke all homebrew by introducing breaking changes to the thread-local storage layout. All homebrew had to be recompiled against the updated libnx. As far as I know, the changes needed to support the new TLS layout didn't break anything after recompilation. Except mono-nx, that is.

After recompiling and testing on the latest firmware, I started observing seemingly random crashes in the runtime when running the same demos included in the mono-nx repo that worked perfectly before. With some extremely painful debugging, I discovered that the issue was caused by the `pthread_key_create` function returning `EAGAIN` when trying to create a new TLS key. This is normally unexpected, and in many cases Mono does not check the return code of `mono_native_tls_alloc`, poisoning the runtime with invalid or colliding TLS keys that eventually cause a crash.

I dug into the libnx implementation and found the root cause: the number of TLS slots depends on the amount of space reserved by the OS. This was [reduced to accommodate for 21.0](https://github.com/switchbrew/libnx/commit/cad06c006e4e0caf9c63755ac6c2a10a52333e27), which reduced the effective number of TLS slots from 27 to just 12, not enough for Mono. While the missing error handling is definitely a bug in Mono and caused me quite the headache, it is yet another case of "we have no other choice but to implement our own version of this API."

In fact, the fix was to implement a custom [fake TLS implementation](https://github.com/exelix11/dotnet_runtime/blob/libnx/src/mono/mono/utils/mono-tls.c#L204) that multiplexes a single TLS slot into many slots using its own internal bitmap. It is not 100% correct, particularly when it comes to destructors, but it is good enough for Mono and the game to run.

## Memory management strikes back

By then, everything had been going smoothly, and I was making steady progress getting the game to work. However, during extended testing, I noticed that after 10 or so minutes of running perfectly, the whole application would just crash with errors pointing to heap corruption. A lucky stack trace directly pinned the issue to `free` calls: my implementation of the memory-management functions naively assumed that `mono_vfree` would only be called with pointers that had previously been allocated by `mono_valloc`. However, it actually expects a full mmap-like implementation that can free arbitrary subsets of pages rather than just the whole allocation. The fix was to create a [fake mmap implementation](https://github.com/exelix11/dotnet_runtime/blob/libnx/src/mono/mono/utils/mono-mmap-libnx.c#L43) that is initialized with a contiguous block of memory during early startup and then uses a bitmap to keep track of page allocations. The memory block is taken by [stealing it from the libnx heap](https://github.com/exelix11/mono-nx/blob/fec057748af9121d5cf363e772e817908d57c191/native/shared/heap.c#L51) before it gets assigned to newlib. I currently use a 50% split, but it's not optimal since it effectively segments the real heap into native heap and managed heap. In fact, it does cause OpenGL/Mesa to fail to initialize when running in applet mode. For now, we will have to live with it.

It is worth noting that Mono already has a better [implementation of this concept](https://github.com/exelix11/dotnet_runtime/blob/libnx/src/mono/mono/utils/mono-wasm-pagemgr.c) for WebAssembly, but it is not portable to the Switch since it is 32-bit only. Either way, after some back and forth figuring out the minimum alignment requirements and page sizes, the game was finally stable and playable for long sessions without crashing.

While I was working on this, Nautilus from discord also mentioned experimenting with the [MapPhysicalMemory syscall](https://switchbrew.org/wiki/SVC#MapPhysicalMemory), which would allow us to solve this problem in a much cleaner way by providing a real virtual memory mapping API. However, using this syscall requires modifying how the libnx heap works and changing the homebrew ABI. There is an [open issue](https://github.com/switchbrew/libnx/issues/503) on libnx about this, but I do not see it being implemented any time soon, given the limited number of homebrew applications that would benefit from it.

Interestingly, not wanting to deal with mmap was one of the reasons I initially picked Mono instead of coreclr for this project. I am starting to wonder whether it was a good call after all.

Finally, I was also made aware that some people had managed to get [Linux Native AOT games](https://github.com/delsonazevedo/Celeste64-Switch) running on the Switch by compiling them as static AOT libraries and shimming the libc implementation at link time. The whole thing is vibe-coded and full of hacky workarounds for many of the issues I discussed in these porting notes, such as [never freeing memory](https://github.com/delsonazevedo/Celeste64-Switch/blob/switch-port/Switch/native/nativeaot_shims.c#L646-L651). I am not particularly fond of this approach, and I do not think it scales well, since more complex APIs like sockets require manually marshaling newlib C structures and enums to glibc. Still, it was worth mentioning as a sort of "state of the art" for C# on the Switch.

## Misc AOT and runtime improvements

While working on the port, I also enabled a number of APIs from the BCL that were previously not being compiled for the Switch. In particular, `System.Security.Cryptography` now builds, and select classes like `RijndaelManaged` and `AesManaged` are even usable. Abstract classes related to cryptography also work instead of immediately throwing `PlatformNotSupportedException`. The actual native implementation for hashes and cryptography is still not provided, but this allows third-party packages that depend on the common types and enums, such as [acryptohashnet](https://github.com/AndreyRusyaev/acryptohashnet), to provide some of the missing features. This required a single change in the `.csproj` of the cryptography library to enable support for our platform and has greatly improved the usability of the runtime.

AOT compilation also improved thanks to the `direct-pinvoke` compilation flag, which previously would not link because of the missing native crypto static library. It is now possible to link C# P/Invoke calls directly to native libraries without going through our very slow fake `dlopen` implementation. This measurably improved in-game frame times and also allows the linker to strip unused libraries from the final binary. When using the latest mono-nx, this change is a single-line difference in the AOT build script, and it is already present in the demo programs.

## Debugging the undebuggable crash

One unresolved issue from Part 1 was a crash that happened when running another homebrew application after returning to the hbmenu from mono-nx. This issue required me to introduce the `exit_process_on_end` flag, which forces mono-nx to exit the process when the main thread ends instead of returning to the hbmenu.

After thinking about the problem, reading old conversations on Discord, and going through the source code of libnx, I finally figured out the root cause: the Switch OS is not POSIX, and the way threads work in libnx requires the application to manually clean up their stack space before exiting. What happens is that [threadCreate](https://github.com/switchbrew/libnx/blob/master/nx/source/kernel/thread.c#L132) maps the stack memory with `svcMapMemory`. The backing memory for this comes from `__libnx_aligned_alloc`, which uses the same heap as the rest of the application. This causes the stack region to be allocated _somewhere_, while the backing pages from the heap region get reprotected as inaccessible. If the application exits without calling `threadClose` on all threads, `svcUnmapMemory` is never called, leaving the heap region with random holes in it. The next homebrew in line has its own allocator, so it reinitializes the heap from scratch using the same runtime-provided heap region. Eventually, `malloc` or equivalent functions touch memory in the holes left by the previous application, causing a crash.

For Mono, unfortunately, I have no fix for the time being. This is because it uses pthreads, which are known to be incomplete on switch. The only way to get the newlib pthread implementation to call `threadClose` [is to use `pthread_join`](https://github.com/switchbrew/libnx/blob/master/nx/source/runtime/newlib.c#L217) as any other way of exiting a thread will not properly unmap the memory, causing the heap holes. Mono uses `pthread_exit` in many places, and that is probably why we fail to clean up on exit.

I did consider using `svcQueryMemory` after mono deinitialization to find the holes and manually unmap them, but it is very hacky and requires knowing the exact source-to-destination mapping of each region, which is impossible when many threads have the same stack size. Even implementing platform-specific threads will not work, because `threadExit` in libnx does not unmap the memory. We would still need another thread to keep track of the thread handles and call `threadClose` on exit. We could implement a global data structure to keep track of them, but it would only add to the pile of hacks. For the time being I decided to leave the `exit_process_on_end` flag enabled and not worry about it.

## Remote debugging

Finally, one last thing I wanted to play with was the Mono debugger. While reading the manpages, I found out that Mono offers a completely software-defined debugger that can be used to debug the C# code running in the interpreter over a TCP connection. This is very useful for debugging the game, since it allows you to set breakpoints and inspect variables, so I wanted to see if I could get it working.

It turned out that this was only one `#ifdef` away from being functional. After that, we could statically link `libmono-component-debugger-static.a` instead of `libmono-component-debugger-stub-static.a` and enable the debugger in the runtime. I introduced support for this in the .inf config file with the `enable_debug_server` field. When this is set to true, the runtime starts a TCP server on port 55555 and waits for a debugger to connect. To connect to it, you can use the VS Code [Mono debugger extension](https://marketplace.visualstudio.com/items?itemName=ms-vscode.mono-debug) (as far as I know, this does not work in the normal C# debugger extension) and set the host to the Switch IP address and port 55555. All these changes are already part of the latest mono-nx release, and a debugging example with a proper [launch.json file](https://github.com/exelix11/mono-nx/blob/master/managed/pad_input/.vscode/launch.json) is provided in the repo.

And just like that, you can attach to and debug your code while it is running on the console. The first time I got this working, it felt almost magical.

The biggest downside is that it is a software debugger, so it cannot break into native code or handle native exceptions, such as an invalid pointer access from either C# unsafe code or the native side.

## Conclusion

With this, we have reached another major milestone in the mono-nx project. The runtime is now stable enough to run real games, and the BCL changes allow it to handle real-world code and third-party libraries from nuget. I am very satisfied with this result. There are still many issues that need to be addressed, such as the lack of JIT and cryptography support, which would make it possible to access the internet over HTTPS, but we are slowly getting there.

In the meantime, I have started to wonder whether CoreCLR would have been a better choice for this project, given that many of the issues I used as motivation for discarding it also happen to be present in Mono. Perhaps in the future I will look into it, mostly to see whether it would provide better ergonomics for handling Switch-specific gotchas like the JIT and threading issues. The good news is that most of the work done for mono-nx is also applicable to CoreCLR since the BCL is shared between the two runtimes, if you're interested in the task please get in touch.

Additionally, as I mentioned in the opening, I would like to try porting another game from Steam using only its binary, to see how difficult it would be to write managed shims and patches to get it working on the Switch. I will carefully consider if/how to proceed, given the potential copyright issues.

One last thing: if you would like to play with mono-nx but cannot be bothered to build the whole .NET runtime fork on your own, I have started releasing prebuilt runtime and compiler binaries under the name "mono-nx sdk". These are automatically built with GitHub Actions and contain all the static libraries needed to build mono-nx projects without the full runtime. For more information, check the README of the mono-nx repo and the [Actions build steps for osu-stream-nx](https://github.com/exelix11/osu-stream-nx/blob/master/.github/workflows/build.yml).

I hope this write-up was useful to anyone interested in porting Mono to other platforms or porting a C# game to the switch. Thank you again for reading until the end.
